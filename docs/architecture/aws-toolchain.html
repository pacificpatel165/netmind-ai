Where Each Piece Fits

A plain-language map of every tool involved in BACKLOG.md item 29 — what LocalStack is, what Terraform is, and why one depends on the other only in one specific, narrow place.

The one-sentence version

Terraform is a construction manager that reads a blueprint and issues build orders in "AWS language"; LocalStack is a mannequin that answers to that language on your own laptop instead of the real AWS servers answering it — nothing else changes.

The whole stack, top to bottom

Everything you typed lives at the top; everything it actually runs on lives at the bottom.

What each name actually means, one at a time

AWS is Amazon's real cloud computing service — actual computers, in actual buildings, that anyone can rent by the hour. LocalStack is a separate, unrelated program that pretends to be AWS: it listens for the same kinds of requests and answers the same way AWS would, but it's really just software running on your own laptop, so nothing costs money and nothing is "real."

Docker is a way of packaging a program (like LocalStack) into a self-contained box called a container, so it can be started, stopped, and thrown away cleanly without touching the rest of your system. WSL2 is Windows' way of running a real Linux computer inside your Windows laptop — the `Containerlab` distro is the specific Linux environment this project already uses for the network lab and Kubernetes.

Terraform is a tool for describing infrastructure you want as a text file, and then having that description made real automatically, instead of clicking through a website or typing commands one at a time. The file you write it in is often called a "blueprint" here because that's exactly the role it plays. The AWS provider is a plugin Terraform downloads that knows how to turn your generic description into the specific request format AWS (real or fake) actually expects — it's the only piece that needed to be told "send your requests to LocalStack, not real AWS," via the four-line address override in main.tf.

awslocal (and its full form, the aws CLI) is a completely different tool from Terraform — you don't use it to build anything, only to look. It sends its own separate requests to LocalStack afterward, asking "what's actually there?" so you're checking with a second, independent tool rather than just trusting the builder's own report.

Matching this to what you actually typed

1

localstack start -d

Tells Docker to launch the LocalStack container — the mannequin wakes up and starts listening on localhost:4566.

2

terraform init

Downloads the AWS provider plugin — the translator — so Terraform is able to speak "AWS" at all.

3

terraform plan

A dry run — Terraform works out what it would build, and shows you before touching anything. Nothing is created yet.

4

terraform apply

The real build — the provider sends the create-VPC, create-subnet, create-security-group requests to LocalStack (because of the address override), and LocalStack hands back real-shaped IDs like vpc-596022934a8a7da49.

5

awslocal ec2 describe-vpcs (and friends)

The independent check — a separate tool walks in and asks LocalStack directly what exists, instead of trusting Terraform's own success message.
