NetMind AI — component #4 (Kubernetes) reference

Cilium, Kubernetes and Docker, on one kernel

Two separate container stacks are now running side by side on the same Containerlab WSL2 distro: the Docker/containerlab stack from components #1–10, and a new k3s cluster with Cilium as its CNI. Neither replaces the other. This is how they actually relate underneath.

1. Two stacks, one kernel

Every container — Docker or Kubernetes — is ultimately the same Linux primitives: namespaces, cgroups, and (for Cilium) eBPF hooks in the kernel. What differs is who's driving. clab deploy talks to dockerd directly; kubectl talks to k3s's API server, which schedules onto its own, separate embedded containerd — not Docker's. They don't share a control plane, and nothing crosses between them unless you wire it yourself.

2. What a Pod actually is

A Pod isn't a container — it's one or more containers that share a network namespace. Kubernetes creates a hidden pause container first, which does nothing but hold that namespace open (one IP, one eth0) for the real containers to join. That's the whole trick: containers in a Pod see each other on localhost because they're genuinely inside the same network namespace, not because of any magic routing.

Getting that namespace connected to the rest of the cluster — so the Pod's IP is actually reachable from other Pods and other nodes — is exactly the job the CNI plugin does. That's where Cilium comes in.

3. How Cilium wires a Pod in

For each Pod, a veth pair is created — two ends of a virtual cable. One end goes inside the Pod's network namespace as eth0; the other stays in the node's root namespace. A traditional CNI (Flannel, plain Calico) would plug that host-side end into a Linux bridge and let iptables handle routing and NAT. Cilium does the equivalent job differently: eBPF programs, compiled and attached by cilium-agent directly at that veth, decide where each packet goes — no bridge, no iptables chain to walk.

Where this project's design goes next

Right now every Pod's traffic between nodes would ride an overlay (VXLAN encapsulation) — Cilium's default, and the right choice for "prove it works" first. The e1-2 interface each SR Linux node reserved back in component #1 is for a later step: switching Cilium to native routing, so cluster traffic rides that real interface directly instead of being wrapped in an overlay. That's genuinely non-trivial and deliberately not attempted until a plain workload is proven end-to-end on what's running now.

TermWhat it actually is

kubeletPer-node agent that asks containerd to create/destroy containers to match what the API server wants.
containerdThe actual container runtime. k3s bundles its own — separate from Docker's, even on the same host.
CNIThe contract Kubernetes defines for pod networking, and the plugin (here, Cilium) that fulfills it.

veth pairA virtual cable: one end in a Pod's namespace as eth0, the other in the node's root namespace.
DaemonSetOne Pod per node, always — how cilium-agent and cilium-envoy are deployed.
kube-proxyThe traditional Service-routing component. Disabled here — Cilium's eBPF replaces its whole job.
